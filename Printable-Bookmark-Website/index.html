On the cutting table: one script, one board, one strip at a time

Printable-Bookmark

I wrote a small Python script, main.py, that reads one Pinterest board of printable bookmarks, follows every pin link on it, and saves each pin page into the folder I run it from. This page lays that work out on the table, step by step, with the numbers taken from the code.

First, what this isThe sheet on the table

My README for this repo is only a title, Printable Bookmark Generator, under the banner. So this page takes its facts from main.py itself, all 137 lines of it. The docstring at the top of the file says what the script does in its own words: it reads the board page, follows every pin link it finds, and saves each pin page into the current folder under the last part of its URL.

That matters for how I describe it here. The name describes the board the script serves. The script itself does not crop an image, lay out a printed page, or make a PDF. It fetches pages and writes files. I would rather say that plainly on the page than let the repo name promise a print step the code never takes.

Run it with python3 main.py, from the folder where I want the pages saved. It needs two packages, named in the header of the file: requests and beautifulsoup4.

# lines 7 to 8 of main.py, in the file header
Run it with:  python3 main.py
Requires:     requests, beautifulsoup4  (pip install requests beautifulsoup4)

Step one, what goes inThe board and the fetch

One board goes in. I keep its address in one constant at the top of the file because it is the only thing a user of this script is expected to change. If I scattered it through the functions, retargeting the script would mean hunting.

18 BOARD_URL = "https://www.pinterest.com/karenfrye376/printable-bookmarks/"
25 PIN_LINK_CLASS = "GrowthUnauthPinImage"
31 TIMEOUT = 15

Those three lines run the whole job. The board is the printable-bookmarks board at that address. Pins are found by one CSS class, GrowthUnauthPinImage. Every request gets a timeout of 15 seconds, set per request, not for the whole run, so a board with many pins can still take longer than 15 seconds in total.

I treat the class name as a maintenance point, not a constant I can trust. Pinterest renames its classes without notice. When that happens, the script finds no pins and says so, instead of quietly saving nothing.

Every fetch goes through one helper. It checks the status in one place, and it keeps a network error and an HTTP error as separate messages, since they point at different fixes.

40     try:
41         response = requests.get(url, timeout=TIMEOUT)
42     except requests.RequestException as exc:
43         print(f"Could not load {url}: {exc}")
44         return None
45     if response.status_code != 200:
46         print(f"Could not load {url}: HTTP {response.status_code}")
47         return None
48     return response

It is a GET only script. Nothing in main.py posts, uploads, or sends form data anywhere. The board page is fetched once, then each pin page is fetched on its own, and a failed pin prints its reason and does not stop the pins after it.

Step two, across the tableHow each file is laid down

There is no sheet layout step to show, and I checked again before writing this page: main.py contains no page size, no margin, no image placement, and no print command. What it lays down is files, one per pin, and the care in this step is in the naming and the writing.

Source1 board, BOARD_URL, line 18. Pin links are the links carrying PIN_LINK_CLASS, found at line 106 with soup.find_all("a", {"class": PIN_LINK_CLASS}).
ParserBeautifulSoup with the built in html.parser, line 99. I used the parser that comes with Python so the install list stays at the two packages in the header.
Relative linksPin hrefs can be relative paths. At lines 110 to 111, a href starting with / gets https://www.pinterest.com put in front of it before it is fetched.

File nameThe last path segment of the pin URL, parsed with urlparse. The fallback name, when the path is empty, is bookmark.
Extension addedNone. Zero. The comment at lines 64 to 66 says why: the pin page bytes are saved exactly as they arrived, and guessing an extension would claim a format I never checked.
Write modeBinary, "wb", at line 85. No decoding step sits between the response and the file.

The naming function strips the trailing slash before it takes the last segment. An earlier version that skipped that step got an empty name and crashed when it tried to write the file. That is written in the code at lines 61 to 63, and it is why the strip step uses urlparse instead of splitting the address by hand.

67     path = urlparse(url).path.rstrip("/")
68     name = path.rsplit("/", 1)[-1]
69     return name or "bookmark"
85     with open(file_name, "wb") as fh:
86         fh.write(response.content)
87     print(f"Downloaded bookmark: {file_name}")
88     return True

Step three, what comes outFiles in the folder, lines on the screen

What comes out is one saved file per downloaded pin, in the current folder, named as above, holding the pin page bytes exactly as they arrived. Plus two kinds of printed line: one per file, shown in the capture above at line 87, and one count at the end.

If nothing downloads, the script does not stay silent. That used to be the behavior, and silent success and silent failure look the same. Now it prints which thing most likely happened and returns 1, so a script chaining off this one can tell the run saved nothing.

I show those printed lines as code, read from main.py, not as output from a run. I did not run the fetch for this page. The board is an outside site, and this rebuild stays inside this repo and its own pages. The run story on this page is told from the code, and I label it that way because a capture I did not make would be a lie in a nicer frame.

The mark in the marginKnown fault, still in the code

It still happens at the current head. If two pins end in the same last URL segment, the second write overwrites the first with no warning, and my count in the caller still goes up for both.

I rechecked this against the code instead of copying the old page. The comment in download_printable_bookmark at lines 80 to 84 states the limit in those words. The write at line 85 opens the file name in "wb" mode, which replaces an existing file of that name, and there is no check for an existing file anywhere in main.py. The function then returns True at line 88, and the caller counts it at lines 115 to 116. So a file can be missing while the final count says it was saved.

I have not hit it on this board, where pin ids differ. I keep the note on the page for the same reason I kept the comment in the code: so it is not a surprise if a saved file ever seems to be missing.

Honest notes, in pencilWhat I am not claiming

  • I made no fresh run of main.py for this page, and no local mode exists to run instead: the file takes no arguments and reads no local files. Every run detail here is read from the code.
  • main.py gives no page size, margin, or image size. I did not invent print dimensions for the strip beside this sheet, or anywhere else on this page.
  • The pin class name can break without any change on my side. If Pinterest renames it, the script saves nothing and exits with code 1, by design.
  • The host for relative links is written in two places, BOARD_URL and the prefix at line 111. If I ever point this at a board on a different host, I have to change both, or the relative links resolve to the wrong site. The code says that at lines 100 to 104, and it is still true.
  • The duplicate name fault above is open. I documented it in the code and on this page. I did not fix it in this website rebuild, because this rebuild does not touch main.py.
